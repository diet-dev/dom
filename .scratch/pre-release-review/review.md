# Pre-release code review: @dietdev/dom

Полный аудит перед релизом: весь `src/`, тесты, демо, packaging, документация.
Метод: чтение кода + эмпирические пробы (временные тесты, удалены после прогона; база зелёная: typecheck чист, 115/115).

Корневой паттерн большинства дефектов один: **диспозеры эффектов привязываются к узлу, который может исчезнуть из дерева** — DocumentFragment растворяется при вставке, `replaceWith` отцепляет заменённый узел, — а `unmount()` обходит только живых детей (`src/bind.ts:17-23`).

## Критические (блокеры релиза)

### R1. `list()` внутри Fragment крашится: `NotFoundError` — [x] ИСПРАВЛЕНО

Фикс: эффект списка привязан к якорному комментарию (`bind(anchor, ...)`), родитель выводится из `anchor.parentNode` на каждом запуске (`src/list.ts`). Якорь переживает растворение Fragment и достижим для `unmount`. Регрессия: `test/fragment-cleanup.test.ts`.

`list` как ребёнок Fragment (в JSX — `<>`): первый reconcile вставляет узлы во фрагмент, вставка в DOM растворяет его, а эффект списка замкнут на мёртвый фрагмент (`src/list.ts:25` — `bind(parent, ...)`, где `parent` — фрагмент). Любое изменение `source` после этого → `parent.insertBefore(node, anchor)` с anchor, не лежащим в `parent` → **runtime crash**.

Воспроизведение (проверено):

```ts
const frag = jsxs(Fragment, { children: [list(source, k, r)] });
const host = div();
host.append(frag);
source.value = [...source.value, "b"]; // NotFoundError: The child can not be found in the parent
```

Сценарий реален: оборачивание куска разметки в `<>` — идиома. Даже без обёртки: `<div><>{list(...)}</></div>`.

### R2. Fragment + signal-ребёнок: эффект переживает `unmount` — [x] ИСПРАВЛЕНО

Фикс: `bindChildSignal` держит маркер в DOM постоянно и вставляет контент перед ним; эффект привязан к маркеру (`src/h.ts`). Маркер переезжает в реального родителя при растворении Fragment и достижим для `unmount`.

`bindChildSignal` привязывает эффект к родителю (`src/h.ts:245`); если родитель — фрагмент, после растворения эффект недостижим для `unmount`. Проверено: после `unmount(host)` изменение сигнала продолжает патчить DOM узла. Утечка подписки + работа вхолостую.

Тот же класс проблемы: `component()`/компонент, возвращающий `<>` с сигналами внутри.

### R3. `Fragment` не экспортирован из корня — README и LEARN учат неверному импорту — [x] ИСПРАВЛЕНО

Фикс: `export { Fragment } from "./jsx-runtime.ts"` в `src/index.ts` (циклических импортов нет).

### R4. Нет LICENSE — npm-блокер — [x] ИСПРАВЛЕНО

Фикс: добавлен `LICENSE` (MIT) и поле `"license": "MIT"` в `package.json`.

## Высокие

### R5. Дубли ключей в `list()` оставляют зомби-узлы

`src/list.ts:30-44`: при двух одинаковых ключах создаются два entry; `pending`-Map при следующем reconcile держит только последний → узел первого entry никогда не удаляется. Проверено: `[{id:1,a},{id:1,b}]` → после `{id:1,c}` в DOM остаются **два** `<li>`: старый «a» + новый «c». Фикс: девалер/консоль-warn на дубли +/или пропуск дублей.

### R6. Controlled-режим 2 (plain value + onChange) замораживает поле навсегда

`README.md:144` обещает «контролируемость как в React». Фактически (проверено): `value` запоминается при создании (`src/h.ts:107-114`), ввод сбрасывается к нему, но обновление внешнего состояния в `onChange` ничего не меняет — механизма переприменения пропса нет. Поле навечно показывает стартовое значение, `filter.value` при этом расходится с DOM. React-семантику без ререндера не воспроизвести честно — либо документировать режим как «read-only с уведомлением», либо убрать из дока как «контролируемость».

### R7. Signal-обновления `dataset` и `style`-объекта накапливают устаревшие данные

`src/h.ts:158-159` (dataset) и `src/h.ts:217-220` (style): применение нового объекта не стирает ключи предыдущего. Проверено: `signal({a:"1"}) → {b:"2"}` оставляет `data-a="1"`; `signal({color:"red"}) → {marginTop:"8px"}` оставляет `color:red`. Фикс: в `applyProp` перед применением объекта очищать предыдущее состояние (для signal-путь это безопасно — applyProp вызывается на каждое изменение).

## Средние

### R8. `false` в пропсах становится мусорным атрибутом

`src/h.ts:78-79` фильтрует только `null/undefined`. Проверено: `div({ onClick: false })` → `<div onclick="false">`; `title: false` → `title="false"`. Для `on*` в洪ь ложное значение должно игнорироваться; для прочих — вопрос контракта (React пропускает false для не-булевых). Как минимум — игнорировать false для `on*`.

### R9. Falsy-дети: `0` и `NaN` рендерятся как текст — нигде не задокументировано

Проверено: `div(0 && span("x"))` → `"0"`, `div(NaN)` → `"NaN"`. Пропускаются только `null/undefined/false` (`src/h.ts:224`). Классическая ловушка `count && <span>…</span>` при `count=0` — deserves явного предупреждения в README/LEARN.

### R10. Signal-ребёнок c Node: заменённый узел не диспозится

`src/h.ts:249-254`: `replaceWith` отцепляет старый узел вместе с его эффектами от дерева; `unmount` его больше не найдёт. Пока сигнал жив, эффекты и отцепленный узел не собираются GC (сигнал → подписка → замыкание → узел). Анализ по коду (прямой тест невозможен без профайлера). Фикс-направление: `disposeTree(старого current)` перед заменой.

### R11. `ListView.mount()` без защиты от повторного вызова

Двойной mount → два якоря, два эффекта, общий `#entries` → рассинхрон узлов. Стоит кидать ошибку или делать идемпотентно.
